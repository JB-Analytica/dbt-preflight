# dbt-preflight

Warehouse-free CI for dbt pull requests: builds the changed models against synthetic data on
DuckDB, runs their tests, checks house conventions, and leaves one PR comment. Consumed as a
GitHub Action (`action.yml`) and as a CLI (`dbt-preflight`).

## Commands

```bash
uv sync --extra dev
uv run poe check                 # ruff + ty + pytest; must be green before a commit
dbt-preflight run --base-ref origin/main --comment-file .preflight-comment.md
```

`uv run poe` also has `lint`, `fix`, `format`, `type`, `test-quick` as standalone tasks.

## Layout

- `dbt_preflight/` — the tool itself: `cli.py` (typer entrypoint), `checks.py`/`conventions.py`
  (the rules), `dbt_runner.py`/`manifest.py`/`diff.py` (build + impact analysis on DuckDB),
  `github.py`/`report.py`/`summary.py` (the PR comment).
- `examples/webshop/` — the fixture dbt project (built from `webshop.dbml` via model2data)
  that CI's `self-check` job and the scenario recordings run against.
- `docs/scenarios/` — six recorded PR shapes (four must fail, two must pass); regenerated by
  `scripts/scenarios.py`. Read before changing check/report behavior — a change here should
  show up in a re-recording.
- `scripts/` — `demo_repo.py`/`big_project.py`/`scenarios.py`: repo-generation and recording
  helpers, not part of the shipped package.

## How to work

The main session plans, briefs, reviews and integrates; self-contained implementation,
broad searches and doc passes go to subagents on cheaper models (see the jba-core
`delegating-implementation` skill). Small edits are done directly. Keep this section as is —
it is the only copy of the rule a cloud session sees.

## Conventions specific to this repo

This repo *is* dbt-preflight — it is not itself a dbt project, so `jba-core:warehouse-conventions`
and the dbt-project skills apply to `examples/webshop/`, not to the top-level layout.

## Gotchas

- `action.yml` and `dbt_preflight/` change together: CI's `self-check` job runs the action
  against `examples/webshop/.dbt-preflight.yml` on every PR, so an `action.yml` change is
  exercised by the same PR that makes it.
- The scenario recordings under `docs/scenarios/` are generated output — re-run
  `scripts/scenarios.py` after a behavior change rather than hand-editing them.
